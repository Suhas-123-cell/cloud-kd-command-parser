How to read this report. Numbers marked MEASURED come from a command whose raw output is saved in results/ (path given). Statements marked ASSUMPTION are design reasoning or expectations that were not measured. Environment for every measurement: Apple M5 laptop (10 cores, 16 GB), Docker Desktop VM with 10 vCPU / 8 GB, k3d v5 with k3s v1.31.4 (one server node), Ollama 0.40.2 serving phi3.5 (Q4_0) on the host.

Architecture

Host: Ollama + phi3.5 (teacher). k3d cluster cc-kd (from cluster/k3d.yaml): namespace data runs SeaweedFS (S3 API, PVC-backed); namespace pipeline runs a 2-way Indexed Job of teacher workers that read s3://datasets/commands_pool.jsonl, call Ollama through host.docker.internal and write s3://datasets/teacher/shard-i.jsonl. clean.py builds s3://datasets/v1/train.jsonl; training on the laptop CPU produces s3://models/v1/ and /v2/ (+ GitHub Release). Namespace app runs the FastAPI parser (Deployment, Service, Traefik Ingress /parse on localhost:8080, HPA) which downloads its weights from SeaweedFS at start-up with credentials from a Secret.

Task 1 — Object storage and parallel teacher labelling

Implementation. make up creates the cluster from cluster/k3d.yaml, deploys SeaweedFS (chrislusf/seaweedfs:3.80, one weed server -s3 process) in data, generates random S3 keys into the git-ignored .secrets/ and loads them as Secrets, then creates buckets datasets and models and uploads commands_pool.jsonl (results/task4/deployment.txt lists both buckets). The prompt (prompts/teacher_prompt.txt) lists the eight intents with the handout's examples, the three slot rules, five worked examples taken from the handout, and asks for one JSON line. Ollama options: temperature 0, seed 42 (fixed by the handout), plus num_predict 96 and a stop sequence "\n\n": without it phi3.5 appended "Note: …" paragraphs or invented further examples. Validation JSON validity: first-draft prompt 81 %, final prompt 89 %, final prompt + stop 99 % MEASURED results/teacher_prompt_iterations/. The prompt was tuned on validation.jsonl in these two iterations (disclosed: this makes the teacher's validation score slightly optimistic). Replies are stored byte-for-byte as returned (1,896 of them still end in \n).

Sharding (≤ half page). Worker i of N takes the commands whose 0-based line number n satisfies n mod N = i (worker/worker.py: select_shard). The rule is a pure function of the line number, so the shards are disjoint and together cover every line with no coordination, no locks and no shared state; sizes differ by at most one; any worker can be restarted and recomputes exactly the same subset. Round-robin (rather than contiguous blocks) also spreads any ordering in the pool evenly. Each worker writes only its own object teacher/shard-i.jsonl, so there are no concurrent writes to one key. The Job uses completionMode: Indexed with completions = parallelism = 2; SHARD_INDEX comes from the Pod's job-completion-index annotation via the downward API, and SHARD_COUNT=2. Workers re-upload their object every 50 records and, on restart, skip ids already present, so a killed Pod loses at most 50 replies. Both Pods ran at the same time (started 19:19:32Z, finished after 1,481 s and 1,486 s, about 1.0 command/s each) MEASURED results/task1/pipeline_job.txt, worker_logs.txt. The real bottleneck is the single shared Ollama (run with OLLAMA_NUM_PARALLEL=2 on port 11435 for this run; the manifest default is 11434 and make label OLLAMA_URL=… overrides it); more shards would not help without more teacher capacity ASSUMPTION.

The substring test accepts 17 kept values that match only inside a longer word (e.g. time "now" inside "let me know the time", "local" inside "locally"); a word-boundary match would be stricter. Improvement: run Ollama inside the cluster with its own GPU/CPU budget so workers and teacher scale together.

Task 2 — Training the student (sequence-level distillation)

Implementation. training/train.py (plain PyTorch loop + Transformers) fine-tunes EleutherAI/pythia-70m on the first 1,500 records of train.jsonl (last one C1667; 0 overlap with validation). Each example is Command: <text>\nJSON: <teacher reply><eos>; the loss is computed only on the reply tokens. training/config.yaml holds seed 42, learning rate 5e-4, batch size 16, 8 epochs, max length 96, warm-up 5 % and the library versions (Python 3.12, torch 2.5.1, transformers 4.46.3); the seed is set in code and torch.use_deterministic_algorithms(True). make train reads only that file; make train SUBSET=50 trains on the first 50 records. v2 uses seed 7 (make train-v2). Each model is saved as safetensors + tokenizer + version.json, packed into a deterministic tarball (fixed order, mtime 0) whose SHA-256 is line 1 of models/vN/model.sha256 (other lines: every file). Both are in s3://models/v1|v2/ and in the Release; the downloaded model-v1.tar.gz hashes to d0800d71…f15d, equal to line 1 MEASURED.

Note: score.py counts JSON validity without checking the intent list, but the service does; v1 once produced "intent": "alarm_remove", which caused 1 % HTTP 500s under load (Task 4). The service decoder now has a schema-constrained fallback: only when the greedy output fails schema.json it scores the eight allowed intent prefixes by the student's own log-probability, forces the best one and lets the student finish the slots. Valid outputs are untouched; on validation it fired once for v1 (repairing the alarm_remove output) and once for v2 (V010, which it could not repair: the forced intent is followed by only a date key), and the scores above are identical with and without it (*_greedy.jsonl).

Sequence-level vs logit-based distillation (≤ one page)

(a) Sequence-level KD (Kim & Rush 2016) trains the student with ordinary cross-entropy on the sequence the teacher generated (here its greedy, temperature-0 JSON reply), treating it as if it were the ground-truth label: the student learns the teacher's mode, one hard target per input. (b) Logit-based (word-level) KD trains the student to match the teacher's full next-token probability distribution at every position, usually by minimising KL(pteacher,T || pstudent,T) on temperature-softened logits (often mixed with the hard-label loss), so the student also learns the teacher's "dark knowledge" about plausible alternatives. (c) Why it is not possible here. (1) The teacher is reached only through Ollama's generate API, which returns generated text (a 4-bit GGUF build), not the logit vector over the vocabulary at each step; (2) even with logits, phi3.5 uses a 32k SentencePiece vocabulary and Pythia a 50k GPT-NeoX BPE vocabulary, so the two distributions are over different token sets with different boundaries and cannot be compared position by position without a vocabulary alignment; (3) the handout requires training only on the teacher's generated replies. (d) A real limitation of what I did: the student can only be as good as one deterministic teacher reply per command. It copies the teacher's systematic mistakes (full-frame ceiling about the teacher's 41 %), gets no signal about how confident the teacher was, and the cleaning step removes 257 replies where the teacher hallucinated a slot, so commands with no slot information are under-represented in exactly the cases the teacher found hard.

Limitations / improvements. Weights are reproducible with the same seed and versions on the same platform; across CPUs they are not guaranteed bit-identical ASSUMPTION. 8 epochs reach a training loss of 0.018 (likely memorisation; no held-out loss was tracked because validation must not be used for training decisions). Improvements: a held-out split of the teacher data for early stopping; several teacher samples per command; constrained decoding of all four keys rather than only the intent.

Task 3 — The inference service in a container

Implementation. service/app.py (FastAPI/uvicorn, port 8000): POST /parse returns 200 with only the four-key object and headers X-Model-Version (= MODEL_VERSION) and X-Served-By (Pod name from the downward API); /healthz always 200; /readyz 503 until the model is loaded. At start-up a background thread downloads every flat object under MODEL_URI from S3_ENDPOINT (keys from Secret s3-credentials via envFrom), retries 5 times and then exits so Kubernetes restarts it. MAX_NEW_TOKENS caps generation. Every output is validated against schema.json; any failure (or exception) gives HTTP 500 {"error": "invalid_model_output"}; FAULT_INJECT=1 replaces the output with not json before validation (results/task3/fault_inject.txt). Image: python:3.12.8-slim-bookworm, CPU-only torch wheel, every package pinned (38 pins from pip freeze, then pip check), no weights (0 *.safetensors files in the image); built with one command, docker build -t cc-kd/parser:1.0 service/. Size 1.21 GB on disk, 247 MB compressed MEASURED results/task3/image_info.txt. 18 unit tests cover the API contract with a fake model.

Finding: slow matrix multiplies inside the container. At 1 CPU the first image needed ~3.9 s per request. The profiler puts 72 % of the time in aten::addmm and 24 % in aten::mm: torch's linux/arm64 F.linear path (OpenBLAS reports "Core not found, falling back to generic ARMv8" inside the Docker VM) ran the 512→50,304 output layer in 20 ms, while a matmul with a pre-transposed contiguous weight took 5 ms. pretranspose_linears() stores WT once at load time: mean latency on 30 commands fell from 3,927 ms to 704 ms (5.6×) with 30/30 identical outputs MEASURED results/task3/profiling.txt (scripts/profile_linear.py). On x86_64 with MKL this is probably unnecessary ASSUMPTION.

Results under limits (scripts/task3_container_test.sh: docker run --cpus 1 --memory 1g, 50 sequential validation commands) MEASURED results/task3/: 50 × HTTP 200; latency mean 685 ms, p50 694 ms, p95 783 ms, max 885 ms; peak memory 790,515,712 B = 754 MiB (cgroup memory.peak), highest docker stats sample 478 MiB; memory.events oom_kill 0, OOMKilled=false. The gap between the two peaks is page cache from writing and reading the 282 MB weight file during start-up, which the cgroup counts but can reclaim.

Limitations / improvements. One request is generated at a time per replica (a lock; the CPU limit is one core). Batching concurrent requests, int8 weights, or ONNX Runtime would raise throughput; streaming the safetensors file straight into memory would cut the start-up page-cache peak.

Why replies need their own rules, and why order matters (≤ half page). A NACL is stateless: it does not remember that it let a connection in, so each packet, including the reply to an allowed request, is judged only by the rules for its own direction. A browser's request to port 443 is allowed by inbound rule 110, but the load balancer's reply goes out to the client's ephemeral port (1024–65535) and would hit the default deny without outbound rule 110; likewise the app tier's answer from port 8000 comes back in to the load balancer's ephemeral port and needs inbound rule 130. (A stateful security group would allow both replies automatically.) Order: rules are evaluated from the lowest number and the first match wins. A packet from 198.51.100.9 to port 443 matches both "deny 198.51.100.0/24" and "allow tcp 443 from 0.0.0.0/0"; the deny only takes effect because it is numbered 90, lower than 100/110. Numbered 140 it would never be reached for web traffic, and the abusive range could still use ports 80/443 (sample packet S04 checks this). Trade-off: with port-only matching, outbound rule 110 also lets any tcp packet to a port ≥ 1024 leave (e.g. to port 8000 outside the app subnet); NACLs cannot see source ports or connection state, so this is the usual price of statelessness and is why security groups are layered on top.

Everything except secrets and weights is in Git: code, kit, prompt, raw shards, cleaned data, configs, manifests, results. make up builds and deploys the whole system from a fresh clone in three commands (git clone, cd, make up); it downloads both model versions from the Release and verifies them against the committed checksums.
